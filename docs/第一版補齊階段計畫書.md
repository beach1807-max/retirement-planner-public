# 第一版補齊階段計畫書

文件日期：2026-09-02  
文件狀態：規劃草案，尚未授權修改程式碼  
評估對象：目前 `retirement-planner-pwa` 專案  

## 一、評估基準與範圍

本計畫只以下列兩份文件作為產品功能與計算語意的主要依據：

1. `個人與家庭退休資產規劃_PWA_方案統整_2026-09-01 (1).md`
2. `第一版計算契約與決策附錄_2026-09-01.md`（`calculation-contract-v0.1`）

目前程式碼、README、ADR 與其他專案文件只用來判斷「已實作到哪裡」及辨識衝突，不用來取代上述計畫書或擴張產品範圍。

本文件把原計畫中的範圍分為三類：

- **第一版必須完成**：主計畫明確寫為「第一版」、「第一版至少包含」、已定案方向，或是完成第一版核心使用流程不可缺少的內容。
- **第一版保留邊界**：原計畫允許功能簡化或延後，但要求資料結構、服務介面或模組掛載點先存在。
- **可延後**：原計畫明確標為未來、暫緩或第一輪不必完成，且不會破壞第一版的資料語意與擴充邊界。

### 評估結論

目前專案已完成主計畫第二十三章及計算附錄所要求的「第一輪可運作垂直切片」：可建立家庭與成員、輸入簡化資產及投入、按月計算主要規劃人的最早退休月份、保存至 IndexedDB、備份還原並顯示計算提醒。

但目前尚不能視為整份主計畫描述的完整第一版。缺口主要集中在：

- 第一輪資料模型缺少原計畫明列的幣別與逐筆時間戳記，UI 也尚未完整表達資料狀態與共同持分。
- 收入、支出、負債、完整帳戶／持有部位、淨資產與基本不動產資料尚未建立。
- 儀表板只完成部分指標，尚缺退休目標資產、準備率、指定年齡資產、淨資產、投資組合、再平衡、勞保／勞退與資料更新時間。
- 勞保／勞退、法規版本、情境、投資組合／再平衡及手動市場行情尚未實作。
- 主計畫與計算附錄／既有 ADR 對部分「第一版」範圍的定義不一致，必須先確認契約版本與發布邊界。

因此建議分成 **7 個補齊階段**。理由是先修正資料語意與遷移基礎，再補完整財務時間軸，之後才加入會依賴這些資料的法規、再平衡、情境與行情；如此可避免後期因資料模型改動而重寫計算與備份。

## 二、規格衝突與決策閘門

以下項目只標記，不在本計畫中自行改變產品方向。階段 1 完成前須形成書面決策；若改變 `calculation-contract-v0.1` 的既定語意，必須建立新契約版本並保留舊結果可追溯性。

| C-02 | 主計畫第十四章明定第一版手動取得股票、ETF、匯率的最新可用資料；現有 ADR 與 README 將 Market Data Provider 延後。 | 發布範圍不一致。 | 確認手動行情是否為完整第一版發布必要條件；未確認前保留於階段 7，不宣稱已完成主計畫第一版。 |

| C-04 | 主計畫寫明查看範圍由計算引擎決定資料範圍；現有 ADR 及 UI 將家庭／A／B 定義為資產顯示範圍，退休結果始終是主要規劃人的家庭結果。 | 範圍切換的產品語意不一致。 | 確認個人範圍是否只影響資料摘要，或也要產生獨立退休計算；未決前不得讓同一數字看似代表不同範圍。 |
| C-05 | 主計畫要求 Dashboard 只顯示其他模組結果；目前 Dashboard 元件直接篩選與加總資產。 | 顯示層承擔核心財務規則，未來加入負債、持分與匯率後容易產生不同算法。 | 維持主計畫方向：把摘要計算移至應用／領域服務，Dashboard 只接收 View Model。 |
| C-06 | 主計畫要求 `UI → Application Service → Domain → Repository Interface → Adapter`；目前 `App.tsx` 直接呼叫 Repository 與計算引擎。 | Repository 有介面，但 Application Service 邊界尚未實質形成。 | 階段 1 依原架構補上應用服務，不更換既有 React、Dexie 或計算引擎技術。 |
| C-07 | 主計畫第一輪 Asset／Contribution 最低欄位包含原幣金額、`currency`、`createdAt`、`updatedAt`；目前只保存 TWD 換算值與整份 PlannerData 的 `updatedAt`。 | 已低於第一輪明列的最低資料契約，且不利行情、匯率與遷移。 | 階段 1 補齊欄位及向後遷移；既有 TWD 資料以 TWD 原幣安全遷移，不臆測外幣。 |
| C-08 | 主計畫要求共同持有者比例明確保存；目前新增共同資產時 UI 自動將前兩位成員設成 50／50。 | 系統替使用者猜測財務歸屬。 | 改為使用者明確輸入與驗證比例；既有自動建立資料需保留原值並提示確認。 |
| C-09 | 主計畫第二十四章將「第一輪垂直切片」與後續逐步加入項目分開；目前 README 把已完成的垂直切片稱為「第一版功能」。 | 名稱可能造成完成度誤判。 | 在發布定義上分開「垂直切片 v0.1」與「主計畫完整第一版」，不改變既有功能。 |
| C-10 | 主計畫要求首頁顯示退休目標資產與退休準備率；計算附錄 v0.1 未定義這兩項輸入、公式或輸出。 | 若直接用單一倍數或提領率計算，會擅自新增計畫書未定義的財務假設。 | 在階段 1 定義目標資產與準備率的契約語意及測試案例；若需新公式，建立新契約版本。 |

## 四、七階段補齊方案

### 階段 1：契約、資料語意與遷移基線

**目的**：先消除會造成資料不可逆或同一數字多種解讀的風險，確保後續模組能安全掛載。

**要補齊的功能與模組**

- 對 C-01～C-10 形成決策紀錄，特別是「完整第一版」發布定義及是否建立新計算契約。
- 建立實質 Application Service／Planner Service，集中載入、驗證、儲存、計算及 Dashboard View Model 組合。
- 補齊 Asset／Contribution 第一輪明列欄位：原始金額、幣別、`createdAt`、`updatedAt`；保留 TWD 計算值及匯率轉換掛載點。
- 讓使用者明確輸入共同持分，不再自動假設 50／50。
- 補齊投入的 `fixedDate`、`endDate`、Return Profile 目的地，以及伴侶預計退休月份的可編輯路徑。
- 建立統一資料版本遷移與備份相容策略。

| 層面 | 變更 |
|---|---|
| 資料模型 | 擴充 Asset／Contribution 的幣別、原幣值、時間戳與必要來源欄位；建立明確 schema version 演進規則。 |
| 計算邏輯 | `calculation-contract-v0.1` 公式不變；由應用服務組裝與驗證 CalculationInput；Dashboard 摘要移出 UI。 |
| UI | 完整資產／投入編輯、資料狀態、共同持分、固定停止日及伴侶退休月份設定。 |
| 儲存層 | 新增 IndexedDB schema migration；舊 `planner-data-v0.1` 與 backup v0.1 可遷移且不遺失資料；匯入必須先驗證再原子替換。 |

**依賴關係**：無；所有後續階段都依賴本階段。

**第一版分類**：必須完成。這不是新增功能，而是補正第一輪最低欄位與原計畫架構邊界。

**驗收條件**

1. C-01～C-10 均有明確決策紀錄；會改變計算語意者有對應的新契約版本與驗收案例。
2. 舊 IndexedDB 與舊 JSON 備份可升級，原計算結果在契約 v0.1 下保持一致。
3. 所有新舊資料都能識別 schema／contract／rule version。
4. 共同資產持分由使用者輸入，超過 100% 或成員不存在時阻止儲存／計算。
5. UI 可完整建立引擎已支援的四種投入停止規則，且不再出現「產生錯誤後無 UI 修正路徑」。
6. Dashboard 不再自行執行核心財務加總；App 不再直接組裝計算輸入或協調 Repository。
7. 既有計算、備份、IndexedDB 與 PWA 測試持續通過，並新增遷移與共同持分測試。

### 階段 2：完整財務資料與資產結構

**目的**：把簡化退休資產資料提升為主計畫所需的家庭財務基礎，讓淨資產、投資組合、法規與行情有可靠資料來源。

**要補齊的功能與模組**

- Income：月薪／年薪、薪資成長率、其他固定收入、歸屬與資料狀態。
- Expense／CashFlow：平均月支出、家庭層級支出；維持「非逐筆記帳」範圍。
- Liability：房貸、信貸、車貸、其他負債及歸屬。
- Account → Holding → Asset 關係，以及資產類別、地區、幣別、風險分類。
- 基本不動產資料與「納入總資產／退休資產／可動用時間」；不含出售流程與完整房貸攤還。
- 每筆資料的 individual／joint／household、provided／notProvided／notApplicable 與退休使用範圍。
- 完整新增、檢視、編輯、刪除操作及資料完整度摘要。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增 Account、Holding、Income、Expense、Liability；擴充 Asset 分類與所有權；保留基本 Property 類型，不加入進階出售模型。 |
| 計算邏輯 | 建立總資產、總負債、淨資產與家庭／個人範圍摘要服務；薪資不得直接當成 Contribution。 |
| UI | 將家庭資料拆成可維護的成員、收入／支出、資產／帳戶、負債區塊；顯示逐模組資料完整度。 |
| 儲存層 | 為新增實體建立可遷移儲存結構與索引；備份格式納入新實體及關聯完整性驗證。 |

**依賴關係**：依賴階段 1；階段 3、4、5、7 使用本階段資料。

**第一版分類**：核心財務資料、負債與淨資產為必須；基本 Account／Holding／Asset 邊界與分類為必須或至少完整保留；進階交易紀錄可延後。

**驗收條件**

1. 可建立主計畫列出的收入、平均支出、其他固定收入及四類負債，不需逐筆記帳。
2. 家庭、主要規劃人及伴侶的總資產、總負債與淨資產依所有權及持分正確計算，共同項目家庭只計一次。
3. 未提供、明確 0、不適用在所有新增模組中有不同資料狀態與提示。
4. Holding 可關聯 Account 與 Asset 分類；刪除或變更關聯時不得產生孤兒資料。
5. 基本不動產可以只納入總資產、納入退休資產或排除，預設不強制納入退休資產。
6. 備份還原後，所有關聯、狀態、持分與摘要一致。

### 階段 3：完整家庭預測與儀表板閉環

**目的**：讓主計畫的收入、支出、負債、退休資產與指定年齡節點進入同一月份時間軸，補齊首頁核心判斷資訊。

**要補齊的功能與模組**

- Projection Engine 納入收入、家庭支出、負債變動、Contribution 與一次性支出；退休前一般支出與可投入金額不得重複扣算。
- 正向試算指定退休月份的資產，以及既有反向最早退休月份搜尋。
- 退休目標資產、退休準備率及 50／55／60／65 歲等時間軸節點。
- 目前淨資產、名目／實質切換、最後更新時間、資料完整度及納入／排除說明。
- 依 C-03、C-04 決策實作模式欄位或新契約；未決時維持 v0.1 計算語意並清楚標示。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增預測現金流事件／負債餘額輸入及 Dashboard Result／View Model；若擴充退休模式，使用新契約版本。 |
| 計算邏輯 | 建立新的 Projection 輸入／輸出契約以擴充單一家庭月份時間軸、正向試算、目標資產／準備率及指定年齡快照；既有 `calculation-contract-v0.1` 保持可重現。 |
| UI | 補齊首頁核心卡片、指定年齡節點、名目／實質切換、資料更新時間與逐模組完整度。 |
| 儲存層 | 保存計畫設定與資料來源版本；正式資料仍為計算來源，結果可重算，不把 UI 衍生值當核心資料。 |

**依賴關係**：依賴階段 1、2；階段 4、6 將把退休制度與情境結果接入此輸出。

**第一版分類**：完整家庭時間軸、正向／反向試算及首頁核心資訊為必須；分階段退休支出屬原計畫明列未來能力，可延後。

**驗收條件**

1. 同一筆收入、支出、投入不會重複計入；家庭共同現金流不會按成員重複。
2. 正向指定退休月份與反向最早退休月份在同一假設下可互相驗證。
3. 首頁可顯示退休目標資產、準備率、指定年齡資產與淨資產，且數字由領域／應用服務產生。
4. 名目與實質顯示均可追溯至相同月份時間軸，預設仍為今天購買力。
5. 任何結果都呈現基準日、資料最後更新時間、契約／規則版本、重要 Warning 及納入／排除資料。
6. 收入、支出、負債的家庭整合、0／未提供及邊界月份均有單元與 E2E 驗收。

### 階段 4：臺灣勞保、勞退與法規版本模組

**目的**：依主計畫建立獨立退休制度與法規層，不讓法規公式散落在成員、UI 或通用預測引擎中。

**要補齊的功能與模組**

- RetirementSystem 共用介面與臺灣勞保、勞退兩個獨立模組。
- 勞保年資、投保薪資、請領年齡；勞退新／舊制必要資料、專戶、雇主提繳、個人自提與請領設定。
- RuleSet：規則 ID、版本、生效日、來源、查核日及適用條件；法規與報酬／通膨假設分離。
- 各成員獨立計算後，把已確定的退休收入或資產事件放入家庭月份時間軸。
- 不適用、未提供與資料不足的個別提示。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增 LaborInsurance、LaborPension、RetirementIncomeEvent、RuleSet／RuleSource 及成員歸屬。 |
| 計算邏輯 | 新增版本化勞保／勞退計算器及整合 Adapter；通用引擎只接收已整理的外部流入／退休資產事件。 |
| UI | 新增成員別勞保／勞退輸入、資格／結果、資料缺漏與官方規則版本說明。 |
| 儲存層 | 保存使用者制度資料與所用規則版本；規則更新採新增版本，不覆蓋舊結果所引用版本；備份納入引用關係。 |

**依賴關係**：依賴階段 1～3；階段 6 的「勞退自提 6%」情境依賴本階段。

**第一版分類**：模組、資料結構、版本化邊界為必須。完整公式是否也是第一版發布必要條件，依 C-01 決策；未完成公式時只能標示未納入，不得輸出猜測金額。

**驗收條件**

1. 勞保與勞退資料不存放在 Member 本體，且各自有獨立規則計算器。
2. 每次結果可追溯至規則版本、生效日與來源；更新規則不改寫舊版本。
3. A、B 各自計算的退休收入依請領月份進入同一家庭時間軸，不直接相加兩份退休結果。
4. `notProvided` 產生 Warning、`provided = 0` 不產生缺漏提醒、`notApplicable` 不視為缺漏。
5. 官方範例與已確認邊界案例有測試；無規則或資料不足時阻止該制度估算，不影響其他有效資料試算。
6. UI 明示「估算、非主管機關核定」，但不加入計畫書外的理財或投資建議。

### 階段 5：投資組合與資產再平衡

**目的**：把「擁有什麼」與「可投資資產如何配置」分離，依主計畫提供可解釋的偏離提醒。

**要補齊的功能與模組**

- Portfolio 納入範圍、資產分類與目前配置。
- 目標配置及允許偏離範圍。
- 獨立 Rebalancing Engine，比較實際比例與目標比例並產生狀態／提醒。
- Dashboard 顯示投資組合與再平衡摘要；不做自動交易。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增 Portfolio、PortfolioTarget、Allocation、DriftThreshold；引用階段 2 的 Holding／Asset 分類。 |
| 計算邏輯 | 新增獨立再平衡引擎，計算目前比例、目標比例及偏離；不混入退休計算核心。 |
| UI | 新增投資組合設定、配置圖、偏離提醒及 Dashboard 摘要。 |
| 儲存層 | 保存目標配置與範圍；實際配置由持有部位市值衍生，避免重複保存不一致數字。 |

**依賴關係**：依賴階段 1、2；階段 7 的行情更新會觸發重新計算配置與偏離。

**第一版分類**：依主計畫日常流程與首頁資訊，基本投資組合及偏離提醒列為必須；新投入資金最佳化、減少賣出、最小交易次數與稅務考量可延後。

**驗收條件**

1. 總資產與 Portfolio 納入範圍可不同，房屋、勞退等不會被自動視為可再平衡資產。
2. 目標比例合計必須等於 100%，無效分類或負市值不得產生誤導結果。
3. 偏離超出設定範圍時產生可解釋提醒；範圍內顯示正常。
4. 共同持有資產在家庭 Portfolio 只計一次。
5. Rebalancing Engine 無網路、無 IndexedDB、無 UI 依賴，並有邊界比例與零資產測試。
6. 系統只提示配置偏離，不產生計畫書外的個別證券買賣建議或自動下單。

### 階段 6：情境方案與比較

**目的**：依主計畫保留並實作簡化 Scenario，不修改正式家庭資料即可比較退休決策。

**要補齊的功能與模組**

- 基準方案與 Scenario 資料結構、版本及覆寫欄位。
- 至少支援計畫書示例：提早退休、每月增加投入、勞退自提 6%（後者依賴階段 4）。
- 比較可退休年齡、退休時資產、退休準備率與退休收入。
- Scenario 只形成試算覆寫，不直接修改正式資產或家庭資料。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增 Scenario、ScenarioOverride、ScenarioResultRef；保留基準資料版本與所用契約／規則版本。 |
| 計算邏輯 | 由 Scenario Service 把覆寫套用到複製的 CalculationInput，再呼叫既有引擎；不另寫一套退休公式。 |
| UI | 新增建立、命名、比較及刪除情境；清楚區分正式資料與試算值。 |
| 儲存層 | 保存情境定義，不把可重算結果當唯一真實資料；備份包含情境及其版本引用。 |

**依賴關係**：依賴階段 1、3；完整示例比較依賴階段 4；可不依賴再平衡。

**第一版分類**：底層 Scenario 結構為明確必須；簡化比較功能列入完整第一版。AI 自然語言建立情境可延後。

**驗收條件**

1. 建立／執行情境後，正式 PlannerData 完全不變。
2. 相同基準資料、覆寫、契約與規則版本產生相同結果及 hash。
3. 提早退休與增加每月投入的差異可由逐月時間軸解釋。
4. 勞退自提情境只在階段 4 規則與必要資料齊備時可算；否則顯示明確缺漏而非猜值。
5. 比較畫面至少呈現主計畫列出的四項指標，且不同版本不可無提示混比。
6. 備份還原後情境定義與比較結果可重現。

### 階段 7：手動行情、整合導覽與第一版發布驗收

**目的**：補上主計畫指定的手動市值更新流程，完成跨模組整合及完整第一版發布判定。

**要補齊的功能與模組**

- Market Data Provider 介面及股票／ETF／匯率的手動「更新資產市值」。
- 保存最新可用價格、匯率、資料時間與來源；接受計畫書指定的非即時資料範圍。
- 行情更新後依序更新持有部位市值、總資產、Portfolio、再平衡與退休預測。
- 完成主計畫 PWA 導覽：儀表板、資產／負債、投資組合、財務規劃、設定／備份等既有模組入口；名稱可依實際資訊架構調整，但不新增產品範圍。
- 執行完整資料遷移、離線、備份、效能、可用性與跨裝置尺寸驗收。

| 層面 | 變更 |
|---|---|
| 資料模型 | 新增 Instrument、MarketQuote、ExchangeRate、MarketDataStamp／Source；Holding 保存數量與原幣價格所需欄位。 |
| 計算邏輯 | Provider 在應用／基礎設施層取得資料；匯率轉換後才組裝 CalculationInput；計算引擎本身不連網。 |
| UI | 新增手動更新、更新進度、最後成功時間、個別失敗與過期資料 Warning；整理完整模組導覽。 |
| 儲存層 | 快取最近成功行情與匯率，保存來源時間；部分更新失敗不得破壞既有有效市值；備份是否包含快取需依資料可重建性明確決定。 |

**依賴關係**：依賴階段 1、2、5；發布驗收依賴所有被 C-01～C-04 判定為第一版必須的階段。

**第一版分類**：依主計畫屬第一版，但受 C-02 決策閘門約束；開啟 PWA 自動更新、定期更新、即時行情及多市場行情來源可延後。

**驗收條件**

1. 使用者只能主動觸發更新；失敗時保留最後有效資料並顯示價格／匯率日期及 Warning。
2. 不晚於主計畫允許範圍的最新可用價格能正確換算市值；外幣缺匯率時不得默認 1：1。
3. 更新一次後，總資產、Portfolio、再平衡及退休結果使用同一批有時間戳的資料重新計算。
4. Provider 可替換，Domain／Calculation Engine 不含 HTTP、API key 或供應商特定程式。
5. 離線時仍可使用最後保存資料完成規劃與備份，不宣稱行情為最新。
6. 由新建家庭到資料輸入、退休試算、勞保勞退（若列為必須）、再平衡、情境、行情更新及備份還原的主要流程均有 E2E。
7. 所有第一版必須項目通過型別檢查、單元／整合／E2E、正式建置與資料遷移演練；未完成的延後項目在產品與文件中明確標示。

## 六、第一版必須完成與可延後清單

### 第一版必須完成（依主計畫原文）

- 收入／支出基本資料、資產、負債、淨資產及明確歸屬；不做逐筆記帳。
- 完整家庭月份時間軸、正向／反向退休試算、名目／實質金額及重要 Warning。
- 儀表板核心資訊：退休年齡、退休時資產、目標、準備率、年齡節點、淨資產、投資組合、再平衡、退休制度及更新時間。
- Household／Member、三種資料狀態、三種所有權、退休使用範圍與共同持分不重複。
- 勞保／勞退獨立模組及法規版本化邊界；完整公式是否屬同一發布版依 C-01 決策。
- 基本 Portfolio 與獨立 Rebalancing Engine。
- Scenario 底層結構及簡化比較。
- 手動最新可用行情及可替換 Provider；是否列入同一發布版依 C-02 決策。
- IndexedDB Repository、版本化 JSON 備份、資料遷移與完整 PWA 導覽。

### 可以延後（原計畫已明確保留未來或暫緩）

- 完整交易紀錄、平均成本、已實現／未實現損益。
- 股息、稅務成本、交易成本與稅務最佳化提領。
- 多市場行情來源、即時行情、啟動時自動更新與定期更新。
- 多幣別歷史時間序列；第一版仍可在應用層換算為 TWD 後計算。
- 不動產出售流程、租金等進階退休收入、房貸完整攤還與出售優先順序。
- 分階段退休生活費、醫療／長照專用模型；但資料結構不可阻礙未來增加。
- Monte Carlo／隨機報酬。
- 雲端同步、多裝置同步、多人編輯及自動備份。
- AI 自然語言操作。
- 自動下單、個別證券推薦、新投入資金最佳化、最少交易次數及稅務型再平衡。
- FIRE、教育基金、保險規劃、遺產規劃等主計畫列為未來新增的模組。

## 七、執行與發布原則

1. **先完成階段 1 決策閘門，再進入模型擴充。** 未確認 C-01～C-04 與 C-10 前，可以整理介面與測試，但不應宣布完整第一版範圍或更改既有計算語意。
2. **既有 `calculation-contract-v0.1` 必須可重現。** 新收入、負債、退休制度或多種退休模式若改變輸入與事件順序，建立新契約版本，不覆寫舊規則。
3. **每階段都完成垂直驗收。** 資料模型、計算、UI、IndexedDB、備份與測試同階段完成，避免只建畫面或只建資料表。
4. **不把未定案細節寫死。** 法規、行情、退休模式、支出模式及資料供應商使用規則介面、版本與設定值。
5. **不以未提供資料補猜值。** 所有新增模組延續 provided／notProvided／notApplicable，資料不足以 Warning 或 Error 清楚表達。
6. **不擴充計畫外功能。** 各階段只補本文件列出的原計畫缺口；商業模式、帳號系統、投資建議等不納入。

## 八、建議的下一個實際動作

先執行階段 1 的「決策與遷移設計」，交付物應是：

1. C-01～C-04 與 C-10 的產品／計算／發布決策紀錄。
2. `planner-data` 下一版與舊版的欄位差異表。
3. IndexedDB 與 JSON 備份的無損遷移規格。
4. Application Service、Dashboard View Model 與現有計算引擎的邊界圖。
5. 階段 1 的逐條測試清單。

上述五項確認後，才開始修改資料模型與程式碼。這能避免最早一批修改在階段 2、4 或 7 因幣別、法規或範圍語意改變而再次遷移。
